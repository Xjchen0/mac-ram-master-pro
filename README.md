# 🚀 RAM Master | Mac 运存清理大师（终端版）

一个开源的 macOS 内存监控与清理工具，**跑在终端里**。没有 Electron，没有安装包，`node dist/cli.js` 就能开屏。

下面是 80 列终端下的真实输出（未加修饰，包括一次因权限不足的清理失败）：

```
 RAM MASTER                                                    Terminal Edition

 ╭────────────────────────────────────────────────────────────────────────────╮
 │ 内存占用                                                             60.0% │
 │                                                                            │
 │ ############################################.............................. │
 │                                                                            │
 │ 已用                                                               9.60 GB │
 │ 可释放                                                             5.52 GB │
 │ 总计                                                              16.00 GB │
 ╰────────────────────────────────────────────────────────────────────────────╯

 清理未完成（退出码 1）：Unable to purge disk buffers: Operation not permitted
 /usr/sbin/purge 属主是 root:wheel，需要管理员权限才会生效

 c 清理    p 暂停    q 退出                                         每 2 秒刷新
```

---

## ✨ 核心亮点

- **如实汇报，不演动画**：调用系统自带的 `/usr/sbin/purge` 回收不活跃内存。它是 `root:wheel` 属主的**用户态** CLI 而非内核接口，无管理员权限时会非零退出 —— 本工具如实上报退出码、耗时与实际释放量，失败时把错误原文摆出来，不用动画掩盖。释放量为 0 时会写「未测得可释放内存变化」，而不是谎报「已释放 0.00 GB」。
- **底层精准换算**：解析 `vm_stat` 头部拿到真实页大小再换算字节数，同时兼容 4K 页的 Intel Mac 与 16K 页的 Apple Silicon（页大小是内核常量，硬编码会让后者所有读数小 4 倍）。
- **零原生依赖**：只有 `ink` 和 `react` 两个运行时依赖，没有 FFI、没有 node-gyp、不需要编译。数据全部来自 `vm_stat` 与 `sysctl` 两个系统命令。
- **该全屏时全屏，该退出时干净退出**：备用屏（alternate screen）由 Ink 接管，`q` / `Ctrl+C` / `SIGTERM` / `SIGHUP` 四条路径都会还原主屏并把光标显示回来，不会把你的终端留在一片黑屏里。
- **非交互模式自动降级**：stdout 不是终端时（管道、重定向、CI）只采一次样就退出，不会把 `ram-master > log.txt` 灌满重绘帧；采样失败时既打印错误面板，也以退出码 1 收场，方便脚本判断 —— 不会出现「退出码是 1，画面上却还写着正在读取」这种自相矛盾的输出。
- **中文化编程**：代码逻辑采用全中文命名与注释，降低初学者理解成本。

## ⌨️ 快捷键

| 键 | 作用 |
| --- | --- |
| `c` | 执行一键清理（清理进行中会忽略重复按键，避免并发多个 `purge` 把释放量算乱） |
| `p` | 暂停 / 继续轮询（暂停期间迟到的采样结果会被丢弃，不会覆盖画面） |
| `q` 或 `Esc` | 退出 |
| `Ctrl+C` | 退出 |

## 🛠 技术栈

- **终端 UI**：[Ink 8](https://github.com/vadimdemedes/ink)（把 React 渲染成终端字符）+ React 19
- **语言**：TypeScript 5.9，ESM，`module: NodeNext`
- **测试**：Vitest 5 + ink-testing-library
- **运行环境**：macOS，Node.js ≥ 22

## 📦 安装与运行

```bash
# 1. 安装依赖
npm install

# 2. 编译（src → dist）
npm run build

# 3. 运行
npm start
# 或者直接
node dist/cli.js
```

想当成命令用，链接到全局即可（`package.json` 的 `bin` 名是 `ram-master`）：

```bash
npm link
ram-master
```

开发时可以用 `npm run dev`（`tsc --watch`）自动重编译，另开一个终端跑 `npm start`。

## ✅ 测试与类型检查

```bash
npm test            # 跑一遍全部用例
npm run test:watch  # 监听模式
npm run typecheck   # src + tests + vitest.config.ts 全量检查
```

42 个用例全部基于 `tests/fixtures/vm-stat-样本.ts` 里的真实 `vm_stat` 文本样本，以及 ink-testing-library 提供的假 stdout，**不执行任何 macOS 命令**，因此在 Linux CI 上同样能跑（见 `.github/workflows/ci.yml`，CI 里还会额外验证 `dist/cli.js` 的 shebang 没有在编译中丢失）。分三层：

- `tests/memory-stats.test.ts` —— 解析层纯函数：页大小换算、关键字互不污染、畸形输入返回 `null`。其中「同一份页数据在两种页大小下必须恰好相差 4 倍」是钉死页大小硬编码 bug 的回归测试。
- `tests/App.test.tsx` —— 界面行为：加载态、轮询节奏、连续失败阈值（交互 3 次 / 非交互 1 次）、暂停与恢复、清理成功 / 失败 / 零释放三条横幅、动效上下界、卸载后不遗留定时器、非交互模式只采一次并且失败时如实报错。失败横幅那组覆盖的正是旧实现完全静默的路径。
- `tests/组件/仪表盘.test.tsx` —— 进度条：填充列数与百分比成正比、整条正好铺满可用宽度、**0%~100% 逐 0.5% 扫描都不留空列**、越界夹取、保留一位小数，以及只用 ASCII 字符（关掉颜色也看得出形状）。两条回归测试各自钉死一个 Ink 的反直觉行为：「50% 必须画出一半的列数」对应 `flexShrink` 默认为 0（少了显式声明，进度条会只剩一半长而界面毫无异常）；「中间不留空列」对应百分比宽度换算出小数后并排盒子会漏掉一列。

## 👨‍🏫 编程导师笔记 (Mentor Notes)

> **什么是 Inactive Memory (不活跃内存)？**
> 想象你的桌面上堆满了之前看过的书（缓存），虽然你现在没在看，但它们占着地方。当你需要摊开一张大地图时，`purge` 就像是一位管家，迅速把这些没用的书收回书架，把干净的桌面（物理内存）腾出来给你的新任务。

> **为什么「已用内存」和活动监视器对不上？**
> 本工具的口径是 `wired + active + compressor`（联动页 + 活跃页 + 压缩页），直接来自 `vm_stat`。活动监视器的「已使用内存」口径不同：约为 App 内存（匿名页）+ 联动内存 + 已压缩，且**不计入** `active` 里那部分文件映射页。所以两边差上几个百分点是口径差异，不是算错了 —— 这是刻意选择的取舍：只用一条 `vm_stat` 就能拿到，无需私有 API。实测本工具报 9.6 GB 时，`top` 报 `15G used`，差异全部来自口径。

> **`purge` 需要管理员权限**
> `/usr/sbin/purge` 是系统自带的用户态命令行工具，属主 `root:wheel`。没有提权时它会以退出码 1 失败并输出 `Operation not permitted`。本工具不会绕过权限、也不会替你 `sudo`，而是把退出码和错误原文如实显示出来 —— 看到失败提示是正常的，说明你没有以管理员身份运行。

> **为什么进度条用 `#` 和 `.`，不用 `█` 和 `░`？**
> 两个原因。其一，`█` 这类字符靠背景色才看得见，一旦 `NO_COLOR`、重定向到文件、或者终端只支持 16 色，整条进度条就会变成一行空白（实测确实如此）。其二，`█ ░ ▰` 属于 East Asian Ambiguous 宽度，在开启了「模糊宽度按双宽」的中文终端里会被画成 2 列，而 Ink 按 1 列计算，整行直接错位。ASCII 字符两个问题都没有。

> **为什么进度条的宽度写的是百分比而不是列数？**
> `<Box width="60.0%">` 让 Yoga 自己按父容器宽度算列数，终端 resize 时自动重排，组件既不用监听 `SIGWINCH`，也不用算「边框吃掉几列、内边距吃掉几列」。代价有两个。其一，必须显式写 `flexShrink={0}` —— Ink 的默认值是 0（和 Web 的默认 1 相反），不写的话 512 个字符的填充串会把盒子撑爆，再被 flex 布局挤回一个错误的宽度。其二，百分比换算出来是**小数**（74 列里的 55% = 40.7），如果填充段和空白段是并排的两个盒子，填充段占 `0~40.7`、空白段从 `40.7` 起，取整后第 40 列谁都不写，进度条中间就凭空多出一个空格 —— 实测约一半的百分比都会踩到，而且「填充列数 + 空白列数」的总数照样接近满宽，很容易被子测试的 ±1 容差放过去。解法是把空白段铺满整行当底、填充段用 `position="absolute"` 按百分比盖在上面，取整误差就只会落到条的末端。

> **为什么「连续失败 3 次才报错」在管道里是个 bug？**
> 交互模式下容忍两次失败是合理的：`vm_stat` 偶尔被系统卡一下，闪一次错误面板再恢复反而是噪音。但这个阈值隐含了一个前提 —— **还会有下一次采样**。stdout 被重定向时只采一次，第一次失败就是最终答案，于是画面永远停在「正在读取内存状态…」，进程却已经以退出码 1 结束了。任何「重试 N 次再报错」的逻辑都值得问一句：如果根本不会重试呢？
